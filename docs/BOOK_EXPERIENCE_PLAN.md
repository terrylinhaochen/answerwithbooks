# One book experience, two generated artifacts

Status: implementation plan, 2026-10-09. This document and the prompt templates
are ready for implementation; the reader-generation split and local-package
import described below are not deployed. No new paid generation was run for this
investigation.

## Findings verified in the current code

1. The Smith shelf has two source scopes, not two identical results. The full
   upload and its exact-text duplicate are grouped by extracted-text hash. The
   earlier Chapters 1–3 benchmark has a different hash and is a separate card. `groupBookUploads` has no conceptual-work grouping. Text copied from a
   card also repeats its title because the jacket has face/spine typography and
   the card has a heading; jacket typography is already hidden from assistive
   technology. That is separate from the two-source issue.
2. The old editorial workflow is retained in `scripts/generate-book-wave.mjs`,
   `docs/EDITORIAL_STYLE.md`, and `content-engine/CONTENT_GENERATION_SPEC.md`.
   It produces a roughly 1,500-word, paragraph-led argument with four to six
   idea-led sections. Some catalog pages may have been edited or generated by
   other runs; do not claim one exact prompt produced all historical pages.
3. Private/local conversion uses `distillSection` and `compileDistillation` in
   `supabase/functions/_shared/book-distillation.mjs`. Its `book.md` renderer
   concatenates every chapter summary and application into generic sections.
   The full Smith artifact is 704,379 characters. It is a reference artifact,
   not the finished editorial digest. The recent collapse/overview UI improved
   presentation but did not generate an equivalent reader summary.
4. `BookPurchase.astro`, `BookDigestPersonalizer.astro`, and `FaqList.astro`
   already provide the requested public-page sections. The private page uses
   a separate template, which is why it drifted.
5. `book-library` is authenticated retrieval, not a server executing downloaded
   skills. It ranks chapter methods using vector and keyword search and returns
   bounded methods, source excerpts and citations. The user's current agent
   does the reasoning. A live owner-authenticated Smith query returned hybrid
   retrieval, 117/117 embedded sections, no failed sections, and six cited
   matches. This is a functional readback, not a retrieval-quality benchmark.
6. `Download book & skill` creates a ZIP containing the reader/reference
   artifact, `skill/SKILL.md`, chapter notes, glossary, patterns, cheatsheet,
   provenance, extracted `skill/source.txt`, and installation instructions.
   Downloading does not install anything. Installing the folder is optional
   local/offline use; it is not required for hosted retrieval.
7. The customer-agent `local prepare/next/respond/install` route saves a local
   package. There is no finished-package import action in `book-process` or
   `book-library`, and no local-publish command in the installed CLI. Uploading
   the original is not the same as importing the generated artifacts. The docs'
   old “unless you separately choose to upload it” wording was ambiguous.

Decision: managed generation is the default; **Bring your own agent** is the

Verified this round: the local prepare/next/respond/install implementation and
three offline tests pass, the live own-agent guide explicitly says finished
package import is unsupported, and book-library exposes search plus internal
index draining, not artifact ingestion. No import implementation or deployment
is included in this follow-up.

| Path | Intended behavior | Current gap |
| --- | --- | --- |
| Managed generation (default) | Upload source, approve spending limit, generate reader digest and skill, index privately, retrieve from any connected agent | Separate editorial generation and its checks remain planned; existing conversion produces a reference-style book artifact |
| Bring your own agent | Current agent runs the same versioned contracts, saves a resumable package, then automatically uploads/indexes if the user chose their library | AWB workspace sync is implemented locally but not deployed; no external-package import is planned |

Bring your own agent consumes the customer's existing agent plan or provider
usage; it is not necessarily an on-device model. Plain import must not trigger
hosted text generation or a second conversion charge. Indexing, optional cover
creation and optional hosted semantic review have separate costs/policies.
Both paths must converge on the same reader, skill and retrieval contract.

### Source fidelity: observed failures and design response

The saved evaluations show derived checklists labeled as author instructions,
qualified claims becoming universal, and numerical meanings changing. The
extraction prompt already says to preserve conditions, cite each idea and label
derived applications. Structural validators check shapes and citation bounds;
they cannot prove that cited text supports a claim. The default review model
falls back to the generator model, and the own-agent route uses the same agent
for both. Review false acceptance is observed; correlated mistakes are a likely
contributor, not an experimentally isolated cause. The experimental reader-v2
benchmark also generates a separate editorial directly and does not run the
production per-claim skill reviewer on that editorial.

Use a factual evidence brief before either output, retaining source range,
attribution, conditions and numeric meaning. Generate the reader digest and
agent applications separately. Keep derived applications visibly distinct from
author instructions. Review both final artifacts against original cited source,
not only compressed notes. Add focused checks for quantities, polarity,
qualifiers and prescriptive attribution; permit dropping unsupported claims.
Use a separate calibrated review pass for ambiguous claims and record its
provenance. Importing local artifacts must validate the same contract without
trusting a client-written passed flag. A local agent shifts generation cost;
it does not itself solve fidelity.

### Catalog expansion

Import goes to the owner's private library by default. Public catalog growth is
a separate **Submit to catalog** action with explicit publication consent,
source-rights/provenance review, editorial quality review, and work/edition
matching. Publish only approved reader/skill artifacts and permitted source
material. This lets internal editors or contributors use existing agents for
generation without automatically publishing private uploads. Submission and
public promotion remain proposed features, not verified capabilities.

Acceptance for the missing bridge: generate a fixture locally, import it twice
without duplicates, recover from interrupted sync, retrieve its cited methods
through a fresh authenticated agent, and verify there were no hosted text-model
calls or conversion debits during import. Reject cross-account access and invalid
source references. Public publication must require the separate submission path.

## Product decisions

### One gallery entry per work

Introduce an account-owned work identity above source editions, excerpts and
processing revisions. Use verified bibliographic identifiers where available;
normalized title/author provides a candidate match, not permission to merge
unrelated works, translations or editions. A user can confirm ambiguous matches.
Keep ownership checks and original source identities intact.

For this known Smith case, link the full upload, exact duplicate and benchmark
excerpt to one work. Default to the completed full upload, display the familiar
work title, and keep the formal source title and scope in management. Preserve
all existing deep links and files. An excerpt remains explicitly scoped when
opened. Never delete, overwrite, or silently combine evidence from those sources.
Do not infer verified full-book completeness merely from a filename or section
count. Retrieval defaults to the selected work's eligible source revision and
suppresses redundant exact-text evidence; explicitly scoped excerpt requests
continue to use the excerpt.

### One reader-page shell

Use a shared `BookPageShell` and a common data contract for public and private
books. Adapt build-time public content and authenticated private results to it.
Reuse the actual existing purchase, agent-action and FAQ components, extending
them for client-loaded data instead of duplicating their markup and CSS.
Private content remains authenticated and noindex; it is never copied into the
public static collection, page source, sitemap or JSON-LD.

Reader order:

1. Title, author, cover, excerpt scope when applicable, and digest metadata.
2. “When to reach for this book” and “What the book is about.”
3. The complete editorial digest, with meaningful idea-led headings.
4. “KEEP READING / Read the full book.” Reuse `BookPurchase`; show an Amazon
   product link only after checking the actual title/author/edition and saving
   verified metadata. Never reuse The Mom Test's ASIN for Smith or invent one.
   A verified legal full-text link may be offered as an additional option.
5. “Put this book to work.” One copy action that includes the short digest and
   application instructions. It must not copy the entire source and every skill
   chapter into the clipboard. Connected agents can retrieve more evidence.
6. “Book Q&A / How this book is used.” Reuse `FaqList`, with truthful answers
   from metadata and actual answer relationships. A private upload does not
   imply published answers use it; show that fact when there are no relations.

Remove the current skills reference, blanket AI disclaimer, scanner dump,
installation tutorial, full-source download controls, revision controls and
processing dashboard from the normal reader page. Move advanced operations to
an authenticated management surface reachable from the library/processing queue.
Keep actionable failures and material coverage limitations visible where they
matter; do not conceal a failed review or label an unverified artifact verified.
Keep the normal site footer, as on the public book pages.

Hosted retrieval is the default agent experience. Local installation/export is
an advanced option in management/docs. Existing `#use-skill` links should target
“Put this book to work,” not disappear. Existing downloads and skill installation
commands remain supported.

### Two outputs from one evidence pipeline

After source extraction and checked chapter notes, branch into:

- **Reader:** bounded evidence brief -> editorial digest -> source/editorial
  review -> `reader/digest.md` plus an evidence-map sidecar.
- **Agent:** structured methods, scope conditions and source references -> skill
  bundle and hosted retrieval index.

Reuse the old editorial standards for the reader. Keep the newer cited-claim
review and structured extraction for the agent. These serve different purposes;
there is no evidence that the exhaustive reference format is a better reader
summary, or that changing models alone solves the mismatch.

Save independent reader, skill and cover readiness. A failed reader repair must
not discard completed extraction or regenerate the skill. Preserve legacy
`book.md` for compatible exports while switching the reader to `reader/digest.md`.
For existing Smith results, reuse saved notes and source evidence; regenerate
only the editorial artifact after review of the expected cost. Do not force a
complete new conversion or bypass the existing spending approval flow.

Use the [documented prompt registry](../content-engine/prompts/book-digest/README.md).
Hosted and customer-agent generation must consume the same prompt files/schema,
with version/hash recorded per output. Providers may differ without changing the
editorial contract. Prompt templates are documented now; runtime wiring remains
implementation work.

### Finished local package -> hosted retrieval

Choose the destination at intake, independently of who runs generation:

- **My Answer with Books library:** after login, explain that the source evidence,
  editorial digest and structured skill will be stored privately. Selecting this
  destination authorizes automatic upload and indexing when customer-agent
  generation finishes. Do not ask the user to perform another manual upload.
- **This device only:** generate/install offline with no automatic upload. Offer
  “Add to my library” later through the same import protocol.

The cloud destination is the recommended connected flow. It must be explicit in
intake; installing a skill or merely being signed in does not select it. Store
that destination in resumable local job state. A synchronization failure keeps
completed local files and retries the upload, not generation. Show generation
complete and library indexing ready as separate states.

Both paths use a corresponding CLI operation (proposed syntax:
`library import-package ./my-book/package`; not available yet). The connected
flow invokes it automatically with the selected destination. Standalone imports
require login and explain the package and source evidence being uploaded.

Proposed import protocol:

1. Inspect package locally; preview title, source scope, files and byte size.
2. Create an owner-scoped import with an idempotency key and signed upload target.
3. Validate file allowlist, archive paths, file sizes, source/artifact hashes,
   JSON schema, citation ranges, skill structure and review provenance. Reject
   traversal, symlinks, executables and cross-account identifiers; do not execute
   package code or trust an uploaded “passed” flag.
4. Store immutable source and artifacts. Introduce a portable manifest containing
   structured notes and citations, reader artifact/evidence map, source hashes,
   source scope, generator/prompt versions and provenance. Current Markdown-only
   exports must be adapted from the local processing state, or be explicitly
   limited imports; Markdown files alone must not masquerade as a complete index.
5. Mint server-owned work/revision IDs and attach imported source identity.
   Same package hash is idempotent; changes create a revision, not duplicate
   work cards. Preserve section/reference mappings without trusting foreign IDs.
6. Build keyword entries and queue embeddings through the existing indexing
   path. This does not run hosted text generation or regenerate a cover. Show
   pending/ready/failed indexing separately, with resumable retries.
7. Validate ownership and citation retrieval through a fresh connected agent.

Packages missing source evidence may be stored as notes but must not claim
source-verified retrieval. Offer an explicit repair/completion path instead of
silently fabricating citations. Host-run semantic review or a newly generated
reader/cover is a separate optional metered operation requiring an approved
spending ceiling. Package import must not charge the user again for text already
generated locally. Embedding/indexing has an operating cost; define quotas and
accounting explicitly before rollout rather than treating it as zero-cost or
silently debiting conversion credits.

## Implementation sequence and acceptance

1. **Reader contract and prompt integration:** extract the reusable prompt loader,
   implement evidence brief/digest/review states and persist provenance. Compare
   legacy editorial and proposed source-grounded editorial outputs using the
   same evidence, against the current reference artifact as a baseline. Test full
   Smith, its excerpt and one contrasting book with an available authorized
   source. Blind-score fidelity, mechanisms, readability, usefulness and scope;
   track length, latency, tokens and cost. Any unsupported claim fails acceptance.
   No regeneration of the existing public catalog is necessary.
2. **Shared page components:** use one rendering contract; restore purchase,
   practical-agent and FAQ sections, move management away from the reader.
   Verify desktop/mobile, keyboard controls, copy payload size, private auth and
   full/excerpt differences. Purchase links require verified metadata; external
   links open with the same public-component behavior.
3. **Smith migration and work grouping:** explicitly link the known sources,
   generate/review one editorial digest for the selected full upload, keep the
   excerpt separately addressable, and verify one shelf entry plus retained
   source history. Existing deep links, source hashes, skills and charges stay
   intact. Retain old reader artifacts for rollback.
4. **Portable package import:** manifest/export changes, staged import service,
   CLI/browser interface, indexing and documentation. Test duplicate retries,
   interrupted uploads, invalid hashes/ranges, malicious archives, revoked
   sessions, cross-account requests, missing source, and source deletion.
   Verify no text-generation call or conversion debit occurs on plain import.
5. **End-to-end acceptance:** hosted-generated and locally generated examples
   both appear in the same library/page shell; the generic connected skill
   retrieves their cited methods; optional local install still works offline.
   Verify deletion/revocation access, actual stored results and fresh-client

No benchmark winner or completed import capability is claimed by this plan.
